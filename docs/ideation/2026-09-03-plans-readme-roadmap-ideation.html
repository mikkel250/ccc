Grounding Context

Codebase context. CCC is an API-only CV tailor. The finish line is a personal pivot job-search tool, not a frontend or multi-user product. STRATEGY.md owns thesis and tracks; docs/plans/README.md owns build order and status. One Active milestone (currently M4, smoke runner modular + live-API judges). M1–M2 are done; M3 and M4 may both be in progress; M5–M7 are needs plan. Status is manual — no git/CI sync.

Past learnings. M4 should land before M6/M7 eval work. Tenure honesty (M5) is a credibility floor, not a scoreboard. Holistic “strong enough” (M6) is the pivot success signal. Parity (M7) wants a pinned matrix. Judge-model bakeoff is a parked, distinct track — not the same as M6 or M7.

External context. Numbered outcome milestones plus one Active beat a vague Now/Next/Later list for a linear finish line. Stale roadmaps are worse than none. WIP=1 for human+agent teams still needs a place to name parked in-flight work.

  4. finish-line-backlog — personal-tool path vs STRATEGY tracks vs parked bakeoff

1 · agent-what-next

Copy-paste /ce-work path in Active

Description
Put the exact plan path (or /ce-work docs/plans/… argv) in the Active block so a blank /ce-work does not glob the newest implementation-ready file. The roadmap plan itself is currently that newest file. AGENTS already says README Active wins; the skill still glob-selects unless given a path. Programmatic README parsing was deferred — this is the workaround that stays inside v1.

Axis
agent-what-next

Basis
direct: R2 — Active is “the single milestone /ce-work and session start should target.” AE1 — agents must open the linked plan, not the newest date prefix. Roadmap plan defers “AGENTS.md hook telling /ce-work to parse README programmatically.” ce-work blank invocation: glob newest implementation-ready + execution: code.

Rationale
Session start can already read the README and still execute the wrong plan. A visible argv in Active closes that gap without inventing git status sync or a parser.

Downsides
Paths go stale when the linked plan changes; two plans on M4 still need an operator choice. Does not fix blank glob inside the skill itself.

Confidence 85% Complexity Low

2 · wip-active-focus

Name the other in-progress row

Description
Keep dual in progress (M3+M4) — that is intentional. Add one line under Active: Not operating on: M3 — Flexible pivot… so agents do not treat the other in-progress row as equally live. Do not invent paused/yard/timeout statuses; only “parked” already exists, and only for bakeoff in Backlog.

Axis
wip-active-focus

Basis
direct: KTD2 — “M3 and M4 can both show in progress; Active milestone still names exactly one focus.” README table currently shows both as in progress with no visual distinction beyond the Active heading. R2 requires Active to answer “what should I work on next?” without inferring from the table.

Rationale
The table still looks like two live jobs. A single explicit non-focus line is cheaper than a new status vocabulary and still honors WIP=1 for the operator+agent pair.

Downsides
Another line to keep in sync when Active flips. If M3 later becomes Active, the line must move or disappear.

Confidence 75% Complexity Low

3 · remaining-milestones

Seed M5–M7 from existing artifacts now

Description
F3 only fires when Active shows needs plan. While M4 is Active, M5–M7 never get that trigger. Write short plan seeds now by harvesting what already exists: tenure rules in curation-mode.ts and STRATEGY, smoke judges for M6, bakeoff/parity notes for M7 — not three empty greenfield plans. Keep them as linked drafts or “needs plan” with a seed pointer until they become Active.

Axis
remaining-milestones

Basis
direct: F3 trigger is “Active milestone shows needs plan.” M5–M7 rows already say needs plan while Active is M4. STRATEGY already names tenure honesty, holistic “strong enough,” and pinned parity. Prompt-level tenure “NEVER sum overlapping dates” already lives in curation-mode. This is not a claim that those files are done-when for the milestones — only that they are enough to start a plan.

Rationale
The remaining path is the finish line. If planning waits until each row becomes Active, the north-star stays a status table with three hollow rows.

Downsides
Risk of planning the wrong slice too early. Seeds can rot if M4’s smoke shape changes. Must not treat prompt snippets as shipped M5/M6/M7.

Confidence 70% Complexity Medium

4 · maintenance-needs-plan

Last-reviewed / reconciliation line

Description
Add a dated “Last reviewed” (and optionally one-line “what changed”) under How to update. Operator or agent fills it when flipping Active or status. No git-derived automation. Complements the 14-day stale-plan signal, which does not catch a stale README.

Axis
maintenance-needs-plan

Basis
direct: “Status is manual; do not invent automation that syncs from git.” How to update already lists the flip ritual but not when it last ran. Tests only assert Active heading + existing plan links — not that M4 still matches reality. External: stale roadmaps are worse than none.

Rationale
M4 may already be further along on main than the README says. A review date makes “is this north-star current?” a glance, not archaeology.

Downsides
Dates lie if nobody updates them. A false-fresh stamp is worse than no stamp unless How to update treats a missing/old date as a prompt to reconcile.

Confidence 80% Complexity Low

5 · finish-line-backlog

Name the M4→M6→M7 chain in Unblocks

Description
Do not add a Depends-on column. Fill the fields that already exist: M4 Unblocks should name M6/M7 (and bakeoff as parked), Why-active should say the eval chain, not only “operator quality loop.” Leave bakeoff in Backlog — it is judge-model calibration, not M6 holistic success or M7 pinned parity.

Axis
finish-line-backlog

Basis
direct: Why-active already says smoke “unblocks bakeoff / parity.” The table Unblocks cell for M4 only says “Operator quality loop.” M6/M7 Unblocks are outcome phrases, not predecessors. Bakeoff plan parks until smoke lands and treats holistic judge / parity as separate tracks. Finish-line paragraph already exists — this is chain visibility, not a new STRATEGY duplicate.

Rationale
Agents reading only the table miss why M4 is on the critical path to the finish line.

Downsides
Easy to over-claim M5 as optional if the chain is written as M4→M6→M7 only. Tenure honesty still sits on the finish line even if it is not in the eval pipeline.

Confidence 65% Complexity Low

6 · wip-active-focus

Remaining-work on Active (M4 done-when)

Description
Add a short remaining-work / done-when list under Active so “in progress” has an exit. Do not claim smoke U3 is still open — extract may already be on main. The gap is that Active still names M4, links two plans, and has no checklist for what is left (modular runner, live judges, cover-letter DOCX, anything still blocked). Flip to done only when those bullets clear.

Axis
wip-active-focus

Basis
direct: How to update: “When a milestone’s acceptance criteria are met, set its status to done.” Active currently has Outcome + Plans + Why-active, no remaining-work. Tests do not encode M4 completeness. Overrule of “U3 still open”: remaining-work is still useful after a sub-plan lands.

Rationale
Without an exit list, Active can freeze on M4 after the interesting extract work is merged, and the finish line stalls.

Downsides
Easy to turn into a second plan. Keep bullets operator-scale (3–5), not U-IDs duplicated from the linked plans.

Confidence 72% Complexity Low
